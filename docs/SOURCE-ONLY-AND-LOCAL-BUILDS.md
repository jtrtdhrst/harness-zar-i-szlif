# Source-only folders and production image builds

Policy (2026-11-09): retain non-MCP sources in this repository for agent and RepoWise context. Source presence does **not** authorize a Docker build, deployment, or Cloudify/Coolify service creation.

## Two distinct operations

1. **Validation**: lint and unit tests may run on scoped source changes; no Docker image build for source-only folders.
2. **Promotion**: for an actively deployed application, build an immutable image **on the self-hosted build runner** after the reviewed source SHA passes CI. Push the immutable image to a registry, then configure Coolify to pull **that exact digest**. Production must not git-clone and build source independently. Confirm running digest, health, endpoint and rollback before success.

Until a registered, online self-hosted runner and registry publication are verified, **do not** change the live production application's source mode to an image mode: that would interrupt existing releases. No claim that the runner or image release is currently operational.

## Classification

Source-only (no automatic image builds solely because they are in Git): `comfy/`, `plasmic/`, `qdrant/`, `supabase/`, `mautic/`, `opik/`, `paperclip/`, `cloudflare-ingress/`, `shared-ingress/`, `_archive/`, `kod-aplikacji/`, `kod-mcp/`, `docs/`.

Standalone MCP sources (`*-mcp/`) are independently eligible for narrowly scoped CI builds **only after** deployed-resource source binding and release policy verification. `integrations/hermes-paperclip/gateway/`, `integrations/*-overlay/`, `opik-run-enricher/` and `mcp-edge/` are explicit non-MCP or infrastructure exceptions: build only for a specifically approved active runtime, not on every repository push. Never classify by string matching alone when a manifest declares a special case.

For Coolify Git-backed source references used only for RepoWise bootstrap, disable automatic deployment; they are not application release targets. Do not delete them or their source code during repository cleanup.

## Production acceptance criteria

Reviewed commit SHA -> runner-built image digest -> immutable registry artifact -> image-only Coolify deployment -> verified runtime image digest, health/readback, rollback image retained. An image built directly by Coolify from Git **fails** this new local-build-only target even if it serves traffic.

No unrelated source-only path change may trigger an image build, nor can an MCP-only change rebuild non-MCP sources. Tests may still run without building images.

## Harness MCP release admission (ZARI-240, source only)

The Harness delivery controller must not treat a merged pull request as permission to build or deploy. Three repository-owned modules define the fail-closed contract; the privileged controller is expected to call them, and all three are **not installed** on any host by this repository change.

1. `scripts/harness_release_admission.py` — `evaluate(manifest, request, grant, attestation, now)` returns an admission record or raises `Denied` with a stable audit reason. It denies when any of the following is true:
   - the service is unknown, ambiguous, not harness-owned, or its Coolify UUID/kind differs from `ops/release-lanes.json`;
   - the resource is on `hold` (a missing `promotion_state` counts as hold) and no per-UUID grant exists;
   - there is no revocable, unexpired, audited per-UUID grant bound to that exact Coolify UUID and source SHA — a manifest edit is never a substitute;
   - the independent reviewer equals the producer, holds the wrong reviewer role for the lane, or approved a different PR head than the one being released;
   - the source SHA is not the merged main squash SHA, or the base ref is not `main`;
   - the root-owned local-CI attestation is missing, unsigned, not produced as uid 0, **produced by a root-executed test run**, missing a policy digest, stale, failing, empty, or covers paths outside the service root;
   - the immutable image digest is absent or differs from the attested digest.

   Hold is evaluated before any artifact, so satisfying later evidence checks can never promote a held lane. The module is read-only and exposes no force/skip/override switch. Artifacts **and** the attestation key are read `O_NOFOLLOW` with `fstat` on the descriptor that is actually read (re-stat'ed after the read), so a path swapped between a check and a read can never be the bytes that are trusted — the CTO finding on `e52f74f`, whose regression harness observed 35 attacker-controlled reads in 20 000 attempts before the fix and 0 after.

2. `scripts/harness_local_ci_attest.py` — root-invoked attester with **no caller-supplied execution surface and no alternate policy path**: it accepts only `--service`, `--source-sha`, `--base-sha`, `--image-digest`, `--dry-run`. Commands, repository root, output directory, key file and runner uid/gid all come from the root-owned policy `/etc/paperclip-gitops/harness-ci-policy.json` (`0600`, non-symlink, absolute paths). Tests run as the policy's unprivileged `run_as_uid`/`run_as_gid` with `PR_SET_NO_NEW_PRIVS`, an empty supplementary group set, a fresh session and a sanitized environment (no inherited credential, token or proxy variable); **uid 0 execution is refused and never attestable**. The checkout must sit at exactly the requested source SHA with a clean worktree, and policy/key files are opened `O_NOFOLLOW` with `fstat` on the descriptor, closing the symlink-swap/TOCTOU window. The attestation records the policy digest and runner uid, is HMAC-signed, written `0600` under `/var/lib/paperclip-gitops/harness-attestations/<service>-<sha>.json` with an exclusive lock and idempotent reuse. No network credential, no GitHub Actions billing dependency.

3. `scripts/harness_delivery_controller.py` — the reviewed promotion path that *calls* the gate. `run_promotion(manifest, changed_paths, artifacts, transport, ...)` attributes every changed path to a manifest service (a path outside every service root promotes nothing), loads the three root-owned gate artifacts with the same `O_NOFOLLOW`/`fstat` descriptor read as the attester, and calls `evaluate`. On any `Denied` it records the reason and calls **no transport at all** — no build, no deploy, no rollback — so a held, unreviewed, stale or unattributable merge cannot reach Coolify and the running image stays intact. On admission it snapshots the running digest, builds, refuses to deploy when the built digest differs from the attested immutable digest, deploys, requires `health` to report `ok` with the same digest **and** the exact source SHA it was promoted from (a readback that omits either field is refused, never treated as passing), and performs exactly one rollback on any failure; a rollback that itself fails is reported as `rollback_failed` with the error class and an `audit_id` rather than raised, and an unrecordable promotion state also restores the previous image, so every outcome is an auditable report and no failure escapes as an exception. Successful promotions are recorded atomically in `/var/lib/paperclip-gitops/harness-delivery.json` under an exclusive lock, with an `audit_id` over the whole report. The host unit supplies its existing docker/Coolify transport (`current`/`build`/`deploy`/`health`/`rollback`); the module itself never contacts a provider. `--plan` reports the decisions without a transport and mutates nothing.

4. `scripts/harness_native_delivery.py` — the reviewed replacement for the root-owned `harness_image_delivery.py`, mirroring its audited transport (docker build/push to the loopback registry, Coolify compose image-line patch with a compose backup, deploy, health/stability polling, compose rollback) and adding the admission the installed controller lacks. It is two-stage and neither stage can mutate without its gate: `--mode prepare` requires `harness_release_admission.evaluate_build` (manifest allowlist, Coolify UUID/kind, merged-PR head, `main` base, lane hold answered by a live per-UUID grant, independent exact-SHA review) and only then runs `docker build`/`push`, labelling the image with `org.opencontainers.image.revision=<source_sha>`; `--mode deploy` goes through `harness_delivery_controller.run_promotion`, i.e. the full `evaluate` with the root-owned local-CI attestation and the immutable digest, and its transport `build` only **resolves** the already-prepared digest (verified against that revision label) and never rebuilds, so a deploy can never ship source the attester did not see. `health` reads back the running image's repository digest and revision label, `rollback` restores the newest compose backup. Coolify UUIDs are not duplicated here: they come from `ops/release-lanes.json`, which the gate cross-checks.

5. `scripts/harness_install_preflight.py` + `ops/harness/INSTALL-RUNBOOK.md` — the read-only half of the privileged installation. The preflight never writes a host file, never stops or starts a unit and reads no secret: it verifies that the timer and oneshot service are inactive, that each staged module matches the `sha256` of that file at the exact approved SHA, that installed files and the policy/key are root-owned with the right modes, and it refuses to print an install plan while any precondition fails. The runbook lists the operator-only ordered steps (stop timer → back up the hold-blind controller → stage modules from the exact SHA → verify digests → install policy/key → negative canaries while still disabled → re-enable → rollback), including the exact rollback that restores the previous controller.

**Not claimed here:** nothing is deployed or installed by this change, and namespace-level network isolation for the test run is *not* implemented by these modules. The remaining owner/controller steps are (a) install the modules above, the policy file and the attestation key on the approved host, and (b) change the existing root controller `harness_image_delivery.py` to call `harness_delivery_controller.run_promotion` with its current build/deploy/rollback functions in place of its own promotion branch, then read back that a held lane produces no build and no deploy. Network isolation of the test runner and the exact policy contents are part of that audited host activation, not of this source change. Until (b) is installed and read back, the installed controller behaviour is unchanged and no hold is enforced at runtime.

**Known same-defect sibling path (not owned by ZARI-240):** `paperclip-mcp/gitops/paperclip-mcp-auto-release.py` verifies merged PR, CI and native review but never consults `ops/release-lanes.json`, so it can auto-release `paperclip-mcp` while the manifest holds it. That path belongs to the `paperclip-mcp` owner and needs its own bounded change and review.
