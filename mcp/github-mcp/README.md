## Fail-closed defaults

- Hard-coded repository ceiling: `jtrtdhrst/harness-zar-i-szlif`, `jtrtdhrst/zar-i-szlif`.
- `POST /mcp` requires either a constant-time checked `GITHUB_OPS_CALLER_TOKEN` or a cryptographically verified Cloudflare Access JWT restricted to the configured issuer, application AUD and owner email. The Cloudflare path requires `CF_ACCESS_ISSUER`, `CF_ACCESS_AUD`, `CF_ACCESS_OWNER_EMAIL` and Cloudflare Managed OAuth on the Access application. For GitHub API calls use the existing Coolify GitHub App: the independent host refresher mints a read-only installation token, and the `GITHUB_OPS_TOKEN_FILE` runtime path points to a private **read-only directory-mounted** `token.json`. A legacy `GITHUB_TOKEN` is accepted only when no token file is configured; a bad token file always fails closed. No PAT or private GitHub App key is injected into the container.
- `GITHUB_OPS_WRITES_ENABLED` defaults to false. `GITHUB_OPS_WORKFLOWS` defaults to `release-lanes-policy.yml` only. `GITHUB_OPS_WRITER_TOKEN_FILE=/run/secrets/github-ops/writer.json` is a separate, rotating GitHub App grant for explicit owner-authorized writes (including branch creation, feature-branch file commits, pull requests, exact-SHA merges, SHA-verified cancellation and safe branch-delete git leases). The old environment-provided `GITHUB_OPS_PUSH_TOKEN` is no longer accepted by production code; absent writer file denies mutations. Tests may inject credentials through explicit in-process configuration. `GITHUB_OPS_PINNED_BRANCHES` lists branches a live Coolify application tracks (default `feat/github-ops-mcp-20261120`); those are refused even when everything else passes. Keep it in sync with `ops/release-lanes.json`.
- `GET /health` is a liveness endpoint; `ready=false` explicitly means **not operational**, even if Coolify reports the container healthy.
- `tools/call` always returns `structuredContent` as a JSON **object**, never a bare array. GitHub list endpoints are wrapped with their own key and a `count` (`{deployments:[...],count}` / `{rulesets:[...],count}`), so an empty result is an empty list inside an object. A provider reply that is not a list fails closed (`DEPLOYMENTS_INVALID` / `RULESETS_INVALID`) instead of being emitted as a non-conforming payload.
- No generic shell, no arbitrary GitHub URL, no self-approval, branch protection mutation, auto-merge, token provisioning, Coolify deploy, HOLD bypass or implicit user delegation.
- The 12 additional tools are 8 reads (`github_get_file`, `github_get_branch`, `github_list_branches`, `github_list_pull_requests`, `github_get_pull_request`, `github_get_pr_files`, `github_get_check_runs`, `github_get_workflow_runs`) and 4 writes (`github_create_branch`, `github_commit_file`, `github_create_pull_request`, `github_merge_pull_request`). New write tools enforce a separate GitHub App grant and `GITHUB_OPS_WRITES_ENABLED=true`; branch creation requires the exact current `main` SHA, branch commits require the exact branch SHA and current blob SHA for modifications, PR creation requires a verified branch SHA, and merges require a configured exact `GITHUB_OPS_MERGE_ALLOWLIST=repo:pr_number@head_sha` plus GitHub's native protection. Never issue generic arbitrary GitHub mutation requests or mutate `main` directly.
- The dedicated `github-ops-writer` role now requires exactly `actions:write`, `contents:write`, `pull_requests:write` and `metadata:read`; the original reader remains strictly read-only. Without App permission approval, a projected root-owned writer token file, and explicitly enabled writes the new mutation tools return `WRITE_DISABLED` or `WRITE_CREDENTIAL_MISSING`. Setting the flag is an operator task after independent review and writer-credential E2E; updating server source alone does not enable writes or refresh the ChatGPT client's cached tool schemas.
- `github_preview_branch_delete` verifies exact source SHA, a merged PR whose head SHA is exactly this branch head, a reachable merge commit, no open PR reference, no protection and no repository rules. It NEVER deletes. `github_delete_merged_branch` performs the same checks and then deletes **through the git protocol with an expected-SHA lease**: `git push --force-with-lease=refs/heads/<branch>:<expected> <remote> :refs/heads/<branch>`. The receive-pack delete command carries the old oid, so a push that lands after verification makes the server reject the lease (`STALE_LEASE_REJECTED`) — the ref and the concurrent commit survive. This replaces the unsafe REST `DELETE /git/refs`, which has no expected-SHA precondition. The command is an argv list (no shell), the push token is passed in the child environment (never argv, never a URL), and the result is read back: HTTP 404 afterwards, otherwise `DELETE_NOT_CONFIRMED`.
- `github_dispatch_workflow` is NOT exposed. GitHub `workflow_dispatch` with `ref: main` can run a different commit if main advances after checking SHA. Checking the run later detects the problem too late. Calls fail closed before any GitHub request (`TOOL_UNKNOWN`, zero provider traffic). No tool advertises a `workflow` input any more.
- A client that still lists `github_dispatch_workflow` has a stale cached tool table, not a live capability. The server never re-adds it; reconcile by re-initializing/re-registering the MCP server in the client (re-read `tools/list`) and confirm the advertised count is 20. That reconciliation is a client/connector-owner action, not a server change.
- Branch protection/ruleset endpoints may reply HTTP 403 due to GitHub App scopes or private-repository plan limitations. Never treat that as protection enabled.
- All writes must satisfy the separate existing CTO review, release HOLD, CI and operator access boundaries. This service does not enforce the complete GitHub→Coolify promotion policy.

## Run and check

`npm test` — HTTP-level and local-git positive/negative regressions (45 tests at this revision). These include disabled workflow dispatch, missing authentication, fail-closed branch deletion (writes disabled, missing push credential, pinned branch, stale SHA, protection, repository rules, unknown rule state, no merged PR), and a schema-invariant regression that every advertised tool returns object `structuredContent` for empty and non-empty GitHub lists. The lease tests run against a throwaway local bare repository: a stale expected SHA is rejected and the ref survives; the exact SHA deletes it; a push that lands between verification and delete is refused by the lease. A rules endpoint that answers 403 "Upgrade to GitHub Pro" (private repo, no rulesets possible) is accepted only together with `protected: false`; any other 403 stays fail-closed. They make no real GitHub provider writes.

`PORT=3000 GITHUB_OPS_CALLER_TOKEN=<secure-secret> GITHUB_OPS_TOKEN_FILE=/run/secrets/github-ops/token.json node server.mjs`

The host's existing `multica-zar-github-app-refresh.service` reads its existing Coolify GitHub App and mints `github-ops-reader` with five read-only permissions (actions, administration, contents, deployments, metadata), plus a separate `github-ops-writer` grant scoped to Actions write, Contents write, Pull Requests write and Metadata read. These grants must be approved on the GitHub App before replacing the current runtime. `ops/harness/credentials/github-ops-token-project.py` projects the reader JSON under `/etc/github-ops-mcp/reader/token.json` and, when the writer grant exists, the writer JSON under `/etc/github-ops-mcp/reader/writer.json` (root:1000, 0640) after refresh. Mount the whole `/etc/github-ops-mcp/reader/` directory read-only at `/run/secrets/github-ops` in the BGH container; mounting just the token file is incorrect because atomic rotation changes the inode. The private key remains in Coolify; the runtime reads the renewed token per provider request, verifies identity, repositories, permissions, expiry and file ownership. Keep all writes disabled.

Deletion additionally needs the `git` binary in the image (the Dockerfile installs it) and the separate, rotating `GITHUB_OPS_WRITER_TOKEN_FILE` grant. Global Git configuration is suppressed and the credential helper restricts protocol, host and exact repository path. The deprecated `GITHUB_OPS_PUSH_TOKEN` environment variable is not accepted in production.

Use a Coolify **private, manual** staging application with `base_directory=/github-mcp`, `Dockerfile` build and `is_auto_deploy_enabled=false`. No FQDN, no public port, no production secrets in build args. Do not turn on writes/deletion in a test deployment. Register its private MCP URL in Multica only after independent authorization, a supported secure secret injection path, and test of the exact target runtime's network reachability.

## MCP verification

- `initialize` then `tools/list` (authenticated): twenty tools.
- `github_get_deployments` for an exact SHA with no deployments returns HTTP 200 and `{"repo":...,"sha":...,"count":0,"deployments":[]}` — an empty list must not break the client schema.
- `tools/call` with repo outside ceiling: `REPO_DENIED` without provider traffic.
- Without a configured valid `GITHUB_OPS_TOKEN_FILE` (or legacy `GITHUB_TOKEN` when no file is selected): `AUTH_NOT_CONFIGURED` or file/scope errors without provider traffic.
- Without caller token or invalid token: 401.
- With a scoped production credential: verify GitHub `repo_info`, `get_deployments` for a known exact SHA, and provider error handling before enabling any write. Independent QA must read back effect and correlate immutable image digest + authenticated live service QA via Coolify.

The current native Multica ZARI-213 isolation HOLD applies: do **not** grant a high-privilege operator server to unisolated agents or move it into production until that trust boundary is independently proven.
